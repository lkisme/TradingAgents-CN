● 这是项目的核心架构。以下是完整概览：

  ---
  TradingAgents-CN 项目结构

  整体架构

  这是一个多代理股票分析系统，使用 LangGraph 编排多个 AI
  代理协作完成股票投资决策。

  用户/前端 → FastAPI (app/) → TradingAgentsGraph → LangGraph 工作流
                                          ↓
                                                MongoDB + Redis 持久化

  LangGraph 节点执行流程

  节点按顺序串行执行（分析师阶段可配置顺序）：

  START
    ↓
  [分析师阶段] 顺序执行（默认顺序：market → social → news → fundamentals）
    每个分析师：Analyst ←→ tools_{type}（工具调用循环）→ Msg Clear（清理消息）
    ↓
  Report Summarizer（综合4份报告）
    ↓
  [投资辩论] Bull ↔ Bear 轮流辩论（条件路由控制轮数）
    → Research Manager（投资决策）
    ↓
  Trader（制定交易计划）
    ↓
  [风险辩论] Risky → Safe → Neutral 轮流（条件路由控制轮数）
    → Risk Judge（最终决策）
    ↓
  END

  关键设计点

  1. 分析师工具循环：每个分析师通过 should_continue_{type}
  条件判断是否继续调用工具，有 tool_call_count 防止死循环
  2. 辩论轮数控制：should_continue_debate 和 should_continue_risk_analysis
  控制辩论轮数（在 conditional_logic.py 中定义）
  3. 分析师顺序串行：注意分析师是串行的（不是并行），通过 selected_analysts
  列表顺序连接
  4. 两种 LLM：quick_thinking_llm（分析师、研究员、交易员）和
  deep_thinking_llm（Research Manager、Risk Judge）
  5. 内存系统：Bull/Bear/Trader/Judge/RiskManager 各有独立的 ChromaDB
  向量内存，支持跨会话学习

● 读完核心代码（setup.py / conditional_logic.py / bull_researcher.py /
  risk_manager.py / trader.py / research_manager.py /
  default_config.py），按对胜率/收益的实际影响排序，问题如下：

  ---
  一、最致命的问题：没有反馈闭环

  整个系统能产出"买/卖/持 + 目标价"，但找不到回测、PnL 
  跟踪、胜率统计模块。后果：

  - 无法知道系统真实胜率，所有"优化"都是盲调。
  - ChromaDB 内存检索"相似情境的过去建议"（bull/bear/trader/judge 共 5 个
  memory），但没有"那次决策对不对"的标签——错误经验被反复强化。
  - risk_manager.py:148 重试全失败时硬编码返回"持有 +
  完整中性理由"，没有标识位，下游若入 memory 就是污染源。

  ▎ 这是 Rule 9（测试验证 intent）层面的缺失。胜率优化的前提是先能测量胜率。

  ---
  二、Prompt 结构性偏置在压低胜率

  1. 强制结论 = 制造幻觉
    - risk_manager.py:46 "不允许回复无法确定或需要更多信息"
    - trader.py:94 "绝对不允许说无法确定目标价"
    - risk_manager.py:35 "只有……才选择持有，避免作为后备"

  LLM 不知道时被迫编数字。不交易本身就是策略，强制表态会把"该弃权"的样本变成噪声
  决策。
  2. Bull/Bear 是律师不是分析师
  bull_researcher.py:51 "建立强有力的论证"，bear 同理。这是 advocacy 模式，不是
  truth-seeking。两个偏置观点经 Research Manager 平均 ≠
  真相，反而压低高置信度时刻的清晰度。
  3. 辩论走形式
  default_config.py:17 max_debate_rounds=1 — Bull/Bear
  各发言一次结束，没有真正交锋。convergence_llm 是可选，不传就只能靠计数。1 
  轮辩论谈不上收敛。

  ---
  三、决策输出缺概率和期望值

  TradeDecision 只有 action / target_price / confidence / risk_score / 
  reasoning。缺：

  - 盈亏比（R:R）：没有止损价、没有"如果错了亏多少 vs 对了赚多少"。即便方向胜率
  60%，R:R = 1:2 仍然亏钱。
  - 仓位建议（凯利分数 / 风险敞口）：confidence=0.8 和 0.6
  在仓位上应该差很多，现在等同。
  - 预期持有期：日内 / 周级 / 月级混在一起，目标价无意义。
  - 失效条件：什么信号出现就退出？没有。

  ---
  四、市场状态盲（Regime Blind）

  所有股票、所有时点用同一组 prompt
  和同一套分析师顺序（market→social→news→fundamentals）。但：

  - 牛市：动量、新闻、情绪权重高
  - 熊市：基本面、估值、风险权重高
  - 震荡市：技术面 / 套利逻辑

  应在入口加一个 Regime Classifier
  节点，根据指数趋势/波动率/利率环境路由到不同的分析师配置和 prompt
  变体。这是高胜率系统的标配。

  ---
  五、数据层问题

  - default_config.py:21-23：online_tools=false、realtime_data=false
  默认。用陈数据做决策直接拉低胜率。
  - conditional_logic.py:225 fundamentals max_tool_calls=1，其他分析师是
  3。基本面工具一次拿不全数据就被强制结束，现状下基本面报告质量是最薄弱环节。
  - 默认 gpt-4o-mini + o4-mini 是省钱档，复杂金融推理掉得很厉害——尤其 Research
  Manager / Risk Judge 这种 deep_think 节点。

  ---
  六、结构性缺陷

  - 单标的单时点：没有跨标的强弱排序、没有时间序列连续追踪、没有组合相关性约束。
  胜率提升的最大杠杆来自"选股"而非"判涨跌"。
  - 报告无冲突检测：Summarizer 把 4 份报告拼接，没有"基本面看空 +
  新闻面看多"如何处理。冲突场景往是 alpha 所在，现在被平均掉了。
  - 风险辩论顺序固定：Risky→Safe→Neutral 循环，Neutral 在 Risk Judge
  前发言，**最近因偏置（recency bias）**会让 Neutral 论点权重虚高。

  ---
  优先级建议（按 ROI 排序）

  | 优先级 | 改动 | 预期影响 |
  |---|---|
  | P0 | 加回测框架 + memory 标注实际收益 | 让系统可被衡量，是其他优化的前提 |
  | P0 | 输出 schema 加 stop_loss / risk_reward / position_size / horizon |
  即便方向不变，仓位和止损能直接救胜率 |
  | P0 | 删掉"必须给目标价/不允许持有兜底"的强制语 | 减少幻觉决策 |
  | P1 | Bull/Bear 改为 truth-seeking（要求列举支持/反驳证据 +
  分配概率），而不是 advocacy | 提高 Manager 信号质量 |
  | P1 | 加 Regime Classifier 节点，路由到不同 prompt | 横跨牛/熊都能用 |
  | P2 | online_tools / realtime_data 默认改 true | 立即解决数据陈旧 |
  | P2 | fundamentals max_tool_calls 提到 3 | 解决数据不全 |
  | P2 | 把 Summarizer 从"拼接"升级为"冲突检测器"，显式输出分歧点给辩论阶段 |
  alpha 来源 |

  ---
  想从哪个切入？P0 三项里回测+反馈闭环是根，但工作量大；**输出 schema
  扩展（止损/盈亏比/仓位）**改动最小见效最快。

  A. 全局性 Prompt 反模式（影响最大）

  1. 强制表态产生幻觉决策（出现在 5+ 个节点）

  | 文件 | 反模式 |
  |---|
  | risk_manager.py:35 | "只有在有具体论据强烈支持时才选择持有，而不是作为后备"
  |
  | risk_manager.py:46 | "不允许回复'无法确定'或'需要更多信息'" |
  | trader.py:94 | "绝对不允许说'无法确定目标价'或'需要更多信息'" |
  | trader.py:70 | "必须提供具体的目标价位，不允许设置为null或空值" |
  | fundamentals_analyst.py:206 | "不允许回复'无法确定价位'" |
  | news_analyst.py:140 | "不允许回复'无法评估影响'" |

  问题：金融市场最重要的能力之一是承认不确定。强制 LLM
  在数据不足时给具体数字，等于训练它编造。

  修复：把"必须给具体数字"改成"必须给带置信度的数字 + 触发条件"。例如：

  - 若数据充分（至少 5 项关键指标可获取），给出目标价 + 置信度 0.6-0.9
  - 若数据不足，给出目标价 + 置信度 0.3-0.5 + 明确标注"低置信"
  - 允许输出 action="弃权"，但必须说明触发哪些 abstain 条件

  2. Advocacy 模式（律师 vs 真理）— 4 个辩论节点

  │        文件         │                       用词                        │

  │ bear_researcher.py: │ "论证不投资的理由"、"揭露弱点"                    │
  │ 46                  │                                                   │
  ├─────────────────────┼───────────────────────────────────────────────────┤
  │ aggresive_debator.p │ "积极倡导高回报"、"质疑和批评保守立场"            │
  │ y:32                │                                                   │
  ├─────────────────────┼───────────────────────────────────────────────────┤

  │ r.py:33             │                                                   │
  └─────────────────────┴───────────────────────────────────────────────────┘

  问题：用词指令角色"找证据支持自己 + 攻击对方"，这是辩论赛思维不是分析师思维。
  结果：每个角色都把弱论据包装得很强，Manager 看到的是噪声水平相近的对立陈述。

  修复：改成 steelman + 概率赋权 模式：

  你是看涨方分析师。任务不是赢辩论，是诚实评估。

  输出必须包含三部分：
  1. 看涨论据：列出 3-5 条证据，每条标注：
     - 证据强度（强/中/弱），依据是什么数据
     - 这个证据反过来想，最强反驳是什么
  2. 主观概率：你认为标的在 [horizon] 内上涨 X% 以上的概率（0-1，理由）
  3. 你方观点的"如果错了"信号：什么数据出现就承认看错？

  Bear 同理，Risky/Safe 同理。Manager
  拿到的是校准过的概率和触发条件，而不是相互攻击的修辞。

  3. 默认计数混淆"分析师 vs 决策者"

  research_manager.py:39 和 risk_manager.py:39 用 past_memory_str 做 RAG，但召回
  的是"过去类似情境的决策建议"，没有标注成败。等于持续强化历史决策模式。Prompt
  还专门说"从过去错误中学习"——但 prompt 拿到的字符串里根本没有错误标注。

  修复（与上次提到的反馈闭环呼应）：召回应改为：

  {past_memory_str}（每条都附实际后续 N 日收益、是否止损、决策准确性标记）

  如果当前 memory schema 不支持，prompt 至少要显式提示 LLM
  "这些只是相似情境，不一定都是好决策，请独立判断"。

  ---
  B. 各节点具体的 prompt 问题

  4. 市场分析师 — 输出格式过度规定（market_analyst.py:170-471）

  预设了非常详细的 7 节模板（基本信息 / MA / MACD / RSI / BOL / 趋势 /
  投资建议），且 analysis_prompt 里还第二次给了一个更长的模板（共 100+
  行格式指令）。

  问题：
  - 强迫 LLM 必须分析 MA+MACD+RSI+BOLL
  四个指标。如果某只股票真正关键的是成交量异动或趋势线突破，LLM 也得编凑全四节。
  - "报告长度不少于 800 字"——指标不显著时被迫填字数 = 噪音。
  - "给出止损位"和"突破买入价 / 跌破卖出价"在分析师阶段就硬性要求，这本是
  Trader/Risk Manager 的工作；分析师强行回答会把噪声带进决策链。

  修复：把"必须包含全部 4
  个指标"改成"仅报告有显著信号的指标（背离/交叉/突破），无信号写 'N/A
  该指标当前无明显信号'"，并删除"≥800字"硬约束。

  5. 基本面分析师 — Prompt 充满恐吓性大写

  fundamentals_analyst.py:184-215 中：

  ⚠️ 绝对强制要求：你必须调用工具获取真实数据！不允许任何假设或编造！
  🔴 立即调用 get_stock_fundamentals_unified 工具
  🚫 严格禁止：- 不允许说'我将调用工具' ...
  现在立即开始调用工具！不要说任何其他话！

  加 system_prompt 又重复一遍 + news_analyst.py:157-176 也是同样模式。

  问题：
  - 大量大写恐吓 + 重复指令对前沿模型基本无效，反而占用上下文（Risk Manager 上次
  prompt 长度就是性能瓶颈）。
  - 这种模式说明开发者在绕过模型偏好用 prompt 强行改行为——通常是工具描述或
  schema 没写清楚，应该回头修工具不是堆大写字。

  修复：删掉所有 🚫🔴⚠️ 重复禁令，改成一句清晰的工作流：

  工作流：
  1. 若 messages 中无 ToolMessage，调用 get_stock_fundamentals_unified(ticker,
  ...)
  2. 若已有 ToolMessage，基于工具结果生成报告，不再调用

  把强制性放在工具的 description 字段和条件路由里执行（已有
  should_continue_fundamentals 计数器机制）。

  6. 货币 / 公司名 prompt 反复出现，本质是数据层缺陷

  每个 agent prompt 都重复"货币是 ¥/$、公司名是 X、不要混淆"。出现至少 7 次。

  根因：传给 LLM 的工具结果里没把 currency 和 company_name
  作为结构化字段强约束。修工具输出 schema 比修 prompt 高效——一次到位，所有 agent
  受益。

  7. 风险辩论 prompt — 三方都在"攻击"，没人"综合"

  Risky/Safe/Neutral 三个 prompt 完全对称，都写"反驳/质疑/挑战其他两方"。结果：

  - Neutral 在 neutral_debator.py:36
  也被定义为"评估上行下行风险"——但因为整个模板套路是"反驳"，Neutral
  实际会反驳两边而不是综合。
  - 三人轮流发言，每人都在防御，Risk Judge 看到的是 3
  段对抗性独白，没有共识基础。

  修复：改 Neutral 为仲裁角色（不是第三方观点）：

  你是风险综合分析师。前置：Risky 和 Safe 已发言。
  任务：
  1. 列出双方一致的事实（不仅是观点）
  2. 列出真正的分歧点
  3. 对每个分歧，给出在何种条件下倾向哪一方
  4. 输出建议的仓位区间和止损区间（不是 buy/sell 决策）

  Risk Judge 拿到的就是已结构化的分歧清单 + 条件，决策质量直接提升。

  8. Trader prompt 同时承担方向决策 + 仓位 + 止损 + 置信度

  trader.py:60-98：要求 Trader 单次给出 action / target_price / stop_loss /
  confidence / risk_score / 详细推理。

  问题：单次推理同时输出 6 个相关但不独立的字段，LM
  会用第一项的倾向带偏后面所有项（自我一致性偏置）。常见症状：confidence
  永远集中在 0.7-0.85，risk_score 永远在 0.4-0.6，因为它们彼此校准而非独立估计。

  修复：拆成两次调用或显式的 chain-of-thought：

  第一步：仅判断方向（买/卖/持有/弃权）
  第二步：在第一步给定方向下，独立估计：
    - 上涨/下跌幅度区间（基于估值锚定）
    - 失败情景（哪些数据如果出现就推翻方向判断）
    - 仓位 = f(方向置信度, 波动率, 流动性)
    - 止损 = f(支撑位, 波动率)

  9. 看涨/看跌 prompt 缺时间维度

  bull/bear 两个 prompt 没要求"在多长时间内成立"。结果：Bull
  用增长故事（3-5年），Bear
  用季度业绩（1季度），二者根本不在同一时间尺度上，Research Manager
  平均后产出无意义结论。

  修复：在 prompt 顶部强制：

  分析时间窗口：{horizon}（例如：未来 5 / 20 / 60 个交易日）
  所有论据必须明确说明在该窗口内的因果链条。
  跨窗口的论据需要折算或剔除。

  horizon 应作为状态字段从入口传入。

  10. Report Summarizer 没看到 prompt，但根据调用链推断

  setup.py:160 调用
  create_report_summarizer(self.quick_thinking_llm)。如果它只是把 4 份报告拼接 /
  摘要——上次已说过这是把冲突信号平均掉的元凶。

  修复方向：Summarizer prompt 必须强制：

  你的任务不是综合，是分歧识别：
  1. 列出 4 份报告中的关键事实（按报告标注来源）
  2. 列出 4 份报告之间的真实冲突点（不是措辞差异）
  3. 列出 4 份报告共同回避的盲区
  不要做平均化的综合。让 Bull/Bear 看到真冲突。

  11. 通用语言层面的小问题

  - 大量 "请用中文"、"请确保所有回答都使用中文" 重复出现 8+ 次：放一次系统级
  prompt 即可，每节点重复浪费 token 和注意力。
  - "请以对话方式呈现，不使用特殊格式"（research_manager / debators
  都有）：但下游 Trader prompt 要求结构化输出。上游让 LLM 
  写散文，下游让它解析散文——这是 SignalProcessor
  出问题的常见原因。统一成结构化中间产物（dict / 标签 + 自由文本），不要让一个
  LLM 解析另一个 LLM 的散文。

  ---
  一、LLM 类型确实影响巨大，但要区分"哪类影响"

  不同任务对模型的需求不一样：

  | 任务类型 | 对模型的核心要求 | 升级的边际收益 |
  |---|---|
  | 工具调用 / 提取数据 | 指令遵循 + tool-use 准确性 |
  中（足够强即可，过度升级浪费钱） |
  | 格式化报告 | 长上下文 + 格式稳定性 | 低 |
  | 多步推理 / 辩论判决 | 推理深度 + 反事实思考 | 极高 |
  | 概率估计 / 校准 | 训练里见过校准任务 + 数学能力 | 极高 |
  | 创造性写作 / 论证 | 表达力 | 低（金融场景不需要） |

  ---
  二、当前分配的具体问题

  问题 1：Trader 用 quick 是最大错配

  setup.py:170 trader_node = create_trader(self.quick_thinking_llm, ...)

  Trader 的任务（trader.py:60-98）是单次输出 6 个字段：方向 + 目标价 + 止损 +
  置信度 + 风险评分 + 详细推理。这是整条链路里最复杂的多目标推理节点。

  - 上游 4 个分析师（quick）+ Bull/Bear（quick）+ Research
  Manager（deep）的所有信息汇总到这里
  - 输出直接进入风险辩论
  - 用 quick 模型 = 链路上最关键决策点用最弱模型

  建议：Trader 必须 deep。

  问题 2：Bull / Bear 用 quick，Research Manager 用 deep — 顺序倒了

  辩论的价值在于双方用强模型刨出真冲突，让一个稍弱模型综合即可。
  现状反过来：用 quick 产出潦草的攻防 → 用 deep 仔细评估这些低质量论据。

  类比：让两个实习生写报告 → 让总监判决。总监再厉害也救不了垃圾输入。

  建议：Bull/Bear 至少要 mid 档（如果只有 quick/deep 二档，建议升
  deep）。Research Manager 的 deep 必要性反而下降——若 Bull/Bear
  输出已经结构化，Manager 用 quick 即可。

  问题 3：Risky / Safe / Neutral 三方辩论同样的问题

  setup.py:173-175 三个分析师全用 quick。Risk Judge 用 deep。

  同样是"垃圾入 → 总监救场"。如果按之前 prompt 优化建议把 Neutral
  改成"仲裁角色"，Neutral 必须 deep（它实际是子裁判）。Risky/Safe 可以保持 quick
  但 prompt 要改 advocacy → steelman。

  问题 4：Convergence 检查用 quick — 这是浪费

  setup.py 注入 convergence_llm=self.quick_thinking_llm。

  判断 Bull/Bear 立场是否收敛是个语义对齐 + 立场识别任务，要求精确度高于速度。
  quick 模型容易：
  - 把"措辞相似但立场不同"误判为收敛 → 提前终止辩论
  - 把"立场已合一但措辞不同"误判为未收敛 → 浪费 token

  但这个节点调用频次低（每轮辩论 1 次），用 deep 成本可控。

  建议：convergence 用 deep，或至少用一个针对分类校准的中等模型。

  问题 5：Reflector / SignalProcessor 用 quick — 高风险

  trading_graph.py:599-600：

  self.reflector = Reflector(self.quick_thinking_llm)
  self.signal_processor = SignalProcessor(self.quick_thinking_llm)

  - Reflector 写入长期
  memory（被未来决策反复检索）。一次错误反思污染所有后续决策。
  - SignalProcessor 把 LM 散文解析成结构化决策。出错直接误用方向/价位。

  这两个节点是杠杆型节点——单次错误放大到所有未来决策。
  建议：Reflector 必须 deep，SignalProcessor 至少要选一个 schema
  遵循能力强的模型（结构化输出友好的 OpenAI / Anthropic 强档）。

  问题 6：分析师用 quick 是合理的，但有例外

  四、单标的范式直接跑池子会出什么问题

  实际跑 10 只股票会暴露这些问题：

  1. 信号不可比

  不同分析师在不同股票上给的"置信度 0.8"含义不同：A 股票的 0.8
  可能是"基本面强劲"，B 股票的 0.8
  可能是"消息驱动"。没有横向校准就无法决定先买哪只。

  2. 资源分配在 prompt 里就有偏差

  risk_manager.py:35 "只有……才选择持有，避免作为后备"——单标的下逼模型表态。
  池子场景下，"持有/弃权"才是正确动作（用资金买更好的标的），但 prompt
  把弃权当兜底惩罚。
  → 直接结果：所有标的都倾向买入，资金分散，丧失选股 alpha。

  3. Memory 跨标的污染

  5 份 ChromaDB
  memory（bull/bear/trader/judge/risk）按"情境相似度"召回，不区分标的。析"贵州茅
  台"时可能召回"五粮液"的过去决策（行业相似），但当前两者基本面差异已经很大。
  单标的范式时是"经验"，池子范式时是"传染"。

  4. 成本呈线性 N 倍

  单只 ≈ 14 个 LLM 调用。池子 100 只 ≈ 1400 次调用。即使并发 10，仍然是 100
  倍单标的成本，且没有任何信息共享带来的 token 节省。

  5. 时序连续性丢失

  池子场景下 "上周已分析过" 的信号应该被复用或增量更新。当前每次 propagate()
  都从零开始，不读上次 state（除了 memory）。

  五、要改造成池子系统，需要新增的层级

  按工作量从小到大：

  Level 1：保持单标的 graph，外加协调层（改造小）

  [Universe Filter] (基于因子/规则筛池)
      ↓
  [Single-Stock Graph × N]（现有 graph，并发跑）
      ↓
  [Cross-Sectional Ranker]  ← 新增
      ↓
  [Portfolio Constructor]   ← 新增（仓位/相关性/约束）
      ↓
  [Execution]

  - Cross-Sectional Ranker：把 N 份单标的报告
  统一打分体系下排序（需先解决信号不可比）
  - Portfolio Constructor：基于排序 + 协方差矩阵 + 资金约束求解（凯利或
  mean-variance）

  改造成本中等：现有 graph 不动，外面套两层。但胜率天花板被单标的 graph 决定。

  Level 2：图内引入跨标的节点（改造大）

  让 LangGraph state 持有 tickers: List[str] 和
  cross_sectional_signals，新增节点：

  - Macro Regime Node（一次判断市场状态，所有标的共享）
  - Sector Allocator（行业层先决定权重，再分到个股）
  - Cross-Stock Bull/Bear（同时给多只股票排序，而非孤立判断）
  - Portfolio Risk Manager（替代当前个股 Risk Manager）

  改造成本高：state 重设计，节点重写，prompt 大量改动，memory schema
  推倒。但这是真正的池子系统。

  Level 3：拒绝 LLM 做组合层（务实路线）

  LLM 不擅长多变量数值优化（仓位求解、协方差估计）。
  更现实的方案：

  - LLM 层：单标的方向 + 概率 + 失效条件（保留现有架构，按 prompt 优化建议改）
  - 代码层：Black-Litterman / Risk Parity / 因子模型做组合配置

  LLM 输出的"主观概率 +
  不确定区间"作为先验喂给数值优化器。这是当前业界混合架构的主流做法。

● horizon（分析时间窗口）的作用：

  当前问题：Bull 用"3-5年增长潜力"论证，Bear
  用"本季度业绩下滑"反驳——二者根本不在同一时间尺度上，Research Manager
  综合后产出无意义结论。

  horizon 的作用：强制所有辩论方在同一时间窗口内论证。例如 horizon=20
  个交易日，那 Bull 和 Bear 都只能讨论"未来 20
  个交易日内该股票上涨/下跌的证据"。

  具体例子：
  - horizon="5个交易日"：短期交易，技术面和消息面权重高
  - horizon="20个交易日"：中期，基本面和技术面并重
  - horizon="60个交易日"：长期，基本面权重最高

  实现方式对比：

  │      方案       │                        说明                         │

  ├─────────────────┼─────────────────────────────────────────────────────┤

  A.1：删除强制语 — 对胜率的影响

  直接影响：减少幻觉决策

  之前 prompt 强制 LLM 在数据不足时也必须给出具体数字和明确方向。这意味着：

  - 之前：数据不足 → LLM 被迫编造目标价 → 置信度虚高（0.7-0.85 区间）→
  执行了不该做的交易
  - 之后：数据不足 → LLM 可以标注低置信度 → 下游可以做仓位缩减或直接跳过

  预期收益：在"该弃权"的样本上不再亏损。这是胜率提升最直接的手段——不是让对的更对
  ，而是让不该做的不做。

  量化估计

  假设当前系统分析 100 只股票，其中 20-30 只是"数据不足但被迫给建议"的噪声决策。
  这些噪声决策的胜率接近随机（~50%）。如果这些样本的 50%
  被标记为"低置信度/弃权"，整体胜率预计提升 3-5 个百分点。

  - 部分分析报告的"确定性"会降低，前端展示上可能看起来"没那么果断"
  - 如果下游没有处理"低置信度"的逻辑（目前没有），这些信号会被浪费——需要后续在 
  portfolio 层或前端添加置信度过滤
